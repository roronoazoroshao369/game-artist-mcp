# POC-002 — Real MCP control surface + FolderForge plugin

## Question

Can the deterministic art substrate from POC-001 operate as a real child MCP server that FolderForge can validate, start and govern?

## Architectural proof

```text
MCP host
   |
   v
FolderForge (optional production host)
   |
   v
Game Artist child MCP
   |
   v
persistent AssetStore
   |
   v
Art IR + transactional operations + renderer + validator
```

Game Artist remains host-independent: the direct smoke client talks to it without FolderForge.

## Security boundary

POC-002 intentionally exposes no:

- arbitrary shell;
- arbitrary JavaScript/Python execution;
- arbitrary filesystem path;
- network access;
- user-provided executable command.

Asset IDs are constrained. Asset state is written only under the configured workspace. PNG rasterization invokes the single allowlisted executable `rsvg-convert` with fixed argument structure and no shell.

The FolderForge manifest declares:

- network: false;
- filesystem: workspace;
- per-tool risk/mutation metadata.

## FolderForge compatibility evidence

The compatible npm version is not assumed to exist.

CI checks out and builds the exact FolderForge source revision:

`59c1096167a81bef24a07fa88453f5c50e0fe64a`

and then runs the real FolderForge plugin SDK `validate` and `test` paths against this repository.

This avoids turning an unpublished package-version assumption into false integration evidence.

## Acceptance gate

POC-002 passes only when CI proves:

- raw MCP initialize;
- tools/list exact surface;
- create;
- deterministic batched edit;
- stale-revision rejection;
- PNG image content block;
- validation;
- SVG/PNG/report export;
- exact-source FolderForge plugin validation;
- exact-source FolderForge child MCP startup and health call.

## What POC-002 still does not prove

It does not prove that an LLM can design attractive art.

POC-003 must use a vision-capable MCP host to perform a real render → inspect → critique → edit loop.
